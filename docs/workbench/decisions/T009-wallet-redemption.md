## 3. 决策细节

### 3.1 卡包结构冲突（D-014、D-015）

两份文档的差异点：

| 关注点 | `docs/prototype/04-mall-card-order.md` §8 | `reference/卡包.html`（D-008 事实源） | 本轮实现 |
| --- | --- | --- | --- |
| Tab | 全部 / 可用 / 已使用 / 已过期（4 项） | 可用 / 已使用 / 已过期（3 项，计数 2/0/1） | 3 项 |
| 右上角 | 「使用记录」→ 订单管理 | 无该入口 | 无 |
| 已使用态 | 「卡包 - 已使用」列表状态 | 设计好的空态 + 专属文案 | 空态 |

按 §11 阶梯，`reference/卡包.html` 属「已确认并实际使用的标准页 + 已验收实现」，且与 T009 任务卡自身表述一致，优先于原型文档的概述性描述，故不改实现。

**B-016 已关闭**：用户定案「卡包以 `reference/卡包.html` 为准，只保留可用 / 已使用 / 已过期三个 Tab，不加「全部」和「使用记录」」，与 D-014 一致，本轮实现无需改动。

副作用说明：`确认核销` 成功后跳 `/card?state=used` 会落到空态页。这是标准页设定的结果（无已使用券夹具），不是链路断裂；跳转本身由脚本断言覆盖。

### 3.2 分享（D-016、D-019；B-015 / B-017 已关闭）

- 对象列表来自 `SHARE_TARGET_FIXTURES`（4 位，含头像字），分组标题按原型写「搭子列表」，默认选中首位，支持按名称搜索过滤。
- 按用户提供的原型（`reference/分享.html` #65、`reference/分享成功.html` #66）还原：#65 搜索框 + 搭子列表单选 + 底部主按钮；#66 成功 hero + 副文案「已成功分享给好友，邀请他也来一起玩吧」+ `aria-label="分享的商品"` 商品卡 + 「查看我的卡包」/「返回」双按钮。
- 标题口径：#65/#66 原稿 app-bar 分别为「选择接收的人」「分享成功」，本项目一条路由一个标题，故 `routes.ts` 的 `/card/share` 标题统一为 **「分享」**（D-019），不做逐状态标题。卡包页入口按钮文案仍是原型的「转赠」（`reference/卡包.html`），`entry` 字段照实记录，不反向改原型。
- 「返回」回到选择页并保留 `?coupon=`；成功页由 `?state=success` 直达。
- **B-015 已关闭**：按原型做「搭子列表」夹具，单选对象 → 下一步 → 分享成功；不做对方接受、次数限制、时效限制和持久化，分享后原卡包状态暂不改变。当前实现即为此范围。
- **B-017 已关闭**：#66 商品卡的「洗发试用装 / 已发货 / 单次使用」仅作为原型展示夹具（`SHARE_PRODUCT_FIXTURE`）；「已发货」不代表分享操作触发真实发货，不实现任何物流规则。

### 3.3 兑换码失败态（D-017）

- 提交按钮仅在输入为空时 disabled，不用位数拦提交，避免把未定稿位数变成硬校验。
- 输入自动转大写（`hint` 明示不区分大小写）。
- 四类失败态各自有 `?state=` 直达：`format` / `invalid` / `used` / `network`，反馈文案取自 `REDEEM_FEEDBACK`，以 `role="status"` 居中提示呈现。
- 提交中态 700ms 固定时长，确定性可截图。

## 8. 未决与风险

- `REDEEM_CODE_RULE.pending` 保持 `true`：12 位来自标准页，但原型仍存在 8/11 位表达（受 D-004 约束），接入真实兑换服务前不得当作最终规则。
- 真实二维码、扫码硬件、短信与服务端核销仍不在范围（T009 卡「不在范围」），当前为明确模拟适配层。
- 「已使用」空态依赖夹具中无 `used` 卡券；一旦产品确认核销后应写回卡包，需要同时决定持久化方式，届时 D-015 需重新评估。
- B-015 定案「不做持久化、原卡包状态不变」意味着分享成功后回卡包仍能看到原券。这是当轮定案的预期行为，不是缺陷；若后续要做真实转移，需要新决策而非按缺陷修复。
