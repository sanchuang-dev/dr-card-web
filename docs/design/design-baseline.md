# 卡博士 H5 设计基线

## 项目定位

`dr-card-web`（npm 包名仍为 `dr-card-ui`）当前是 **卡博士原生 App 内嵌 H5 前端工程**。设计工作不再只服务于静态高保真演示，而是要在真实 WebView、真实数据、真实宿主能力接入后仍保持稳定的视觉与交互结论。

因此设计基线同时约束两件事：

1. `preview` 中的 UI 真相；
2. `dev` / `test` 中工程接入后不能破坏的视觉与交互契约。

设计策略：

> 已确认产品结构保留 + Mockplus / preview 作为 UI 事实源 + Com Design 体系实现 + H5 / WebView 约束下稳定落地

## 事实源优先级

### 1. 当前用户明确确认

当前任务中用户明确拍板的产品、视觉、文案或交互结论优先级最高。

### 2. Mockplus 原型与 `preview`

作为当前 UI 真相，约束：

- 页面信息架构；
- 用户流程；
- 页面布局；
- 交互状态；
- 业务对象；
- 品牌资产；
- 已验收的视觉修订。

Mockplus 负责原型依据，`preview` 负责可运行实现。两者出现冲突时，不由实现者自行猜测，应回到当前确认结论处理。

### 3. Com Design

作为工程设计体系：

- Design Token；
- 基础组件；
- 移动端交互规范；
- 组件复用方式；
- Tailwind 语义映射。

页面优先组合已有组件和 Token，不随手创建新的颜色体系或重复基础组件。

### 4. 《不靠谱的设计历史》

`不靠谱的设计历史/` 只作为历史证据与待确认参考，不是当前规范。

要求：

- 只借鉴能够被当前原型或用户确认支持的局部内容；
- 不直接复制整页、mock 数据或历史交互规则；
- 与当前事实冲突时记录具体冲突并发起确认；
- 未经确认不得据此扩大功能范围；
- 不因仓库清理删除这些历史证据。

## 品牌视觉方向

关键词：

> 年轻、活力、科技、可信

核心语义：

- Gold：会员、权益、高价值内容；
- Orange：行动、转化、重要入口；
- 中性色负责信息层级和大面积背景；
- 品牌艺术素材可以突破通用组件，但必须有明确视觉依据。

避免：

- 大面积金色堆叠造成廉价感；
- 游戏充值式 UI；
- 过度促销化电商视觉；
- 为了“统一组件”抹掉品牌卡片、IP 或关键艺术表达。

## 移动端与 WebView 基线

主要视觉基准仍为 **375 × 812**。

关注：

- 单手操作；
- 触控区域；
- 信息层级；
- 页面节奏；
- 空 / 加载 / 成功 / 错误 / 禁用状态；
- iOS / Android 安全区；
- Home Indicator 与底部固定操作；
- 软键盘弹起后的输入可见性；
- App WebView 返回行为；
- 页面重新进入 / 恢复时的状态；
- 弱网与接口等待对布局的影响。

浏览器截图正确只是 UI 验收的一部分，不能推断 WebView 中一定正确。

## UI 与工程的边界

### `preview`

负责把 UI 做准：

- 视觉；
- 布局；
- 组件；
- 交互状态；
- 响应式 / 移动端表现；
- 稳定 fixture / mock 下的页面验收。

### `dev`

负责在不破坏 UI 结论的前提下接入：

- 真实 API；
- 业务状态；
- Mock/API 切换；
- JSBridge；
- 鉴权；
- 错误与超时；
- App 宿主环境。

工程接入如果导致 UI 必须改变，应把它视为新的产品 / 设计决策，而不是在 `dev` 静默改掉。

## Mock 对设计的要求

Mock 是正式开发能力，但不应成为“只画成功态”的借口。

用于视觉与交互验收的 Mock 至少应支持需要覆盖的：

- 正常数据；
- 空态；
- 加载态；
- 错误态；
- 禁用 / 无权限；
- 长文案 / 边界数据；
- Bridge 不可用或宿主版本不支持等明确场景。

Mock 数据应与真实数据层通过统一业务接口进入页面，不能让页面分别维护两套 UI 逻辑。

## 组件与 Token 原则

- 先查现有组件，再新增；
- 可复用模式沉淀到组件层；
- 一次性品牌艺术画面不强行泛化；
- 公共组件保持 Token 化；
- 不以“统一”为理由显著降低原型还原度；
- 图标优先 Lucide；品牌 / IP 图形使用正式资产；
- 不随意硬编码与现有设计体系冲突的颜色、阴影和圆角。

## 设计验收

纯 UI 变更进入 `preview` 前应至少确认：

- 信息结构与当前需求一致；
- 375 × 812 主基准无明显偏差；
- 关键状态完整；
- 入口与返回路径成立；
- 使用 Com Design / 项目现有组件约束；
- 品牌素材与文案有依据；
- 没有把历史稿或智能体推断冒充成当前决策。

进入正式开发后，还需要继续确认：

- 真实加载 / 错误状态不会破坏布局；
- WebView 安全区、键盘、滚动、返回等环境行为可用；
- JSBridge 不可用时的表现明确；
- API / Bridge 接入后没有改变已确认的 UI 语义。
